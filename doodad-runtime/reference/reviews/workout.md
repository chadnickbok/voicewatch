# Powerlifting parity review

Reviewed 2026-08-10 against the square Wear OS 7 oracle, the production LVGL
renderer, and the V3 image-generated planning references.

## Disposition

**Structurally equivalent; raster-equivalent by policy.** The Wasm-owned
powerlifting flow now covers all twelve approved states: Today, session,
exercise selection, active set, weight editing, set result/RPE, missed-set
recovery, rest, plate loading, exercise switching, summary/PR, and durable
resume.

Every state renders from the same SceneSnapshot in Wear Compose and LVGL.
Parallax reports exact node order and normalized bounds for every compared
node, with zero quality findings in either renderer. Raw pixel identity is not
required because Compose and LVGL retain their platform font rasterizers,
antialiasing, and RGB565 conversion paths.

The app launches directly into useful workout content and does not reserve a
generic app-title bar.

The V3 pass adds four on-watch planning states: training hub, workout builder,
exercise prescription, and strength-goal setup. The execution spine remains
unchanged, while users can now adjust the current routine and a measurable 5RM
goal before starting.

## Contract and implementation

- The Wasm guest in `apps/workout/src/lib.rs` owns navigation, weight, reps,
  RPE, recovery, persistence requests, and resume behavior.
- The twelve semantic AppSpecs are generated by
  `tools/powerlifting_foundations/generate_appspecs.py`.
- The same generator now emits four additional planning AppSpecs for sixteen
  total workout screens.
- Generic controls remain AppSpec text, card, progress, stepper, row, and
  button nodes.
- The bounded domain visuals are the set target, previous performance, RPE
  selector, rest-next-set, plate diagram, and actual-versus-target treatment.
- Compose and LVGL share one 192dp coordinate contract on the 240px square
  profile. No renderer infers workout state.

## V3 design diff

Command:

```bash
python3 tools/powerlifting_foundations/capture_planning.py
```

The capture script drives the real Wasm guest through all four planning
screens, renders the LVGL framebuffer, quantizes the exact 240px generated
target through the same Project Parallax metric, and writes target/candidate,
overlay, and difference images for every screen.

Current audit:

- 4 planning screens captured through the real guest and renderer
- 0 geometry findings
- 0 touch-target findings
- target/candidate contact sheet at
  `reference/powerlifting-foundations/evidence/planning-v3/contact-sheet.png`
- per-screen semantic snapshots, node evidence, pixel metrics, overlays, and
  difference images under `evidence/planning-v3/cases/`

Raw pixel identity is neither expected nor claimed: the targets are
image-generated design references while the candidate is deterministic
RGB565 UI. The diff is used to detect hierarchy, density, palette, clipping,
and control-shape drift. The final candidates preserve the target hierarchy
while using renderer-native typography and the shared 48dp interaction model.
